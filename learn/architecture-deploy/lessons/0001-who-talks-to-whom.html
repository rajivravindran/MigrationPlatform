Architecture deploy · Lesson 0001 · ~20–30 min

Who is talking to whom?

Goal: stop guessing “frontend talks to backend” and name the actual callers. This is the foundation every Docker/K8s interview diagram sits on.

1. The one sentence to burn in

Your browser runs the UI and calls the API over HTTP. Docker and Kubernetes only package and place those programs—they do not replace the browser.

When people say “frontend and backend talk to each other,” they usually mean:

  • Browser (Chrome, Edge, …) → API process (HTTP JSON, with a login token)
  • The API → databases, object storage, workflow engines, etc.

The Next.js “web” container mostly ships JavaScript/HTML so the browser can do that. It is not (in this product’s normal design) the thing that holds your database password and talks to Postgres on your behalf for every click.

2. Diagram: one machine, Docker Compose (conceptual)

┌──────────────┐     HTTPS/HTTP      ┌─────────────────────────────┐
│   Browser    │ ──────────────────► │  host:3000  (web UI files)  │
│  (you)       │                     └─────────────────────────────┘
│              │     HTTPS/HTTP      ┌─────────────────────────────┐
│              │ ──────────────────► │  host:8080  (API)           │
└──────────────┘                     │         │                   │
                                     │         ▼                   │
                                     │  Postgres, MinIO, Temporal… │
                                     └─────────────────────────────┘

Important: lines from the browser go to published ports on the host. Containers on the same Compose network can also talk to each other by service name (e.g. api → postgres). That is a second network: container-to-container. Interviews often fail when someone mixes those two.

3. Two hosts (what you asked about earlier)

  Machine A                         Machine B
  ┌────────────┐                    ┌──────────────────┐
  │ web :3000  │                    │ api :8080        │
  └─────▲──────┘                    │ + postgres etc.  │
        │                           └────────▲─────────┘
        │                                    │
   Browser loads UI                    Browser calls API
   from A                              at http://B:8080

The browser must know the API address. In this repo that is typically NEXT_PUBLIC_API_URL (baked in at build or set for the web app). Different origins (A vs B) is why CORS and cookies/tokens matter—we cover that in a later lesson; today you only need to know the browser is the client of the API.

4. Primary reading (do this before the quiz)

  1. Skim What is a container? — focus on “process in isolation,” not every flag.
  2. Open apps/web/lib/api.ts in the repo and find where the API base URL comes from. You do not need to understand every line—just “browser JS → API URL.”
